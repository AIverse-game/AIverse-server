# 代码审查

遵循根目录 [AGENTS.md](../../../AGENTS.md)。审查任务不进入开发流程，不再启动审查子 Agent。默认只读：不修改源码、状态、变更记录或 Git 索引；需要执行检查时优先使用已有命令，不改配置或安装依赖。

## 明确输入与范围

读取需求与验收条件、指定差异或文件、必要的调用方和相关测试。独立审查以代码和可验证行为为依据，开发者总结只作为定位线索。

先确认比较基线与本次归属。已跟踪改动按传入的基线比较，纳入指定范围内的暂存、未暂存和未跟踪文件。没有首次提交时直接读取指定文件；若提供开始前快照，使用快照区分已有修改。缺少基线或需求时，先完成可独立判断的部分，并明确哪些结论无法确认，不擅自扩大为全仓库审计。

## 检查重点

围绕本次改动检查需求是否满足、行为回归、兼容性、错误路径、状态或数据不变量，以及有实际后果的测试缺口。涉及权限、外部输入或敏感数据时检查相应边界。新增、移动或重命名的文件对照 [文件命名与目录约定](../../rules/conventions.md)，新增或修改的测试对照 [测试约定](../../rules/testing.md)。

报告具体且能解释影响的问题，以代码路径、复现步骤或适用约束支持结论。区分本次引入的问题与已有问题；不把个人风格偏好、无依据的可能性或无关重构建议列为缺陷。可以没有发现，不凑数量。

必要时运行能验证疑点的检查，并报告实际命令和结果。检查无法执行或覆盖不足时，不把检查通过等同于功能正确。复核任务检查原问题是否解决，以及修复是否引入相关回归。

## 输出约定

先列发现，按严重程度排序，每项包含：

- 严重程度：P0 紧急阻断；P1 高影响、应优先修复；P2 一般缺陷；P3 低影响缺陷。
- 文件与尽量小的行号范围。
- 触发条件、实际后果和依据；按需给出修复方向。

随后简述已审查范围、实际验证及限制。没有发现时写“在本次审查范围内未发现可确认的问题”，仍保留验证限制；待确认疑点单列，不伪装成已确认缺陷。

将报告交回调用方，由开发 Agent 修复和维护交接记录。只有明确授权修复时才切换到开发职责。
