# 开发改动

遵循根目录 [AGENTS.md](../../../AGENTS.md)。本 Skill 负责实现；独立审查由主 Agent 另行调用。

## 确定本次范围

- 结合需求、当前状态和相关实现确定可观察的验收条件。较大功能或重构先在客户端 `changes/` 记录目标、范围和验收；重要选择按需记入客户端 `docs/decisions/`。无法访问客户端仓库时，不在当前仓库另建这些目录，把内容写进交接。
- 功能设计按客户端 `docs/design/README.md` 的规则处理：新功能新建设计文档，调整或补充已有功能时修改原设计文档。
- 开始时记录工作区已有改动和本次目标文件。已有修改与本次工作重叠时保留可比较的起点，例如临时副本或补丁，避免把已有问题当成本次引入的问题。
- 没有首次提交或存在未跟踪文件时，不以空的 `git diff` 作为“无改动”的证据；直接检查目标文件，并在交接中说明基线限制。

## 实现与验证

按可独立验证的小步修改。选择能证明需求成立的检查，覆盖相关错误路径和边界；缺陷修复在有价值且可行时增加回归验证。不要编写只复述实现的测试。测试的分层与写法按 [测试约定](../../rules/testing.md)。

检查命令见所在仓库的 [AGENTS.md](../../../AGENTS.md)，选择方法见 [开发流程](../../rules/development.md#验证如何选择)；仓库检查不等于应用检查，未配置或未执行的检查明确报告，不虚构测试或构建结果。文档改动使用相关链接和格式检查。

## 交给独立审查

先自查本次差异，再按 [独立审查调用约定](../../rules/development.md) 启动审查 Agent。交接包括需求与验收、审查范围、可比较的基线、改动文件和实际验证结果；不把开发者自己的结论当成审查结论。

审查 Agent 默认不写文件。开发 Agent 判断发现是否成立，修复确认的问题，运行受影响检查，并将修复后的范围交回复核。复核只针对修复及其影响；若仍有确认的问题，继续处理或如实报告具体阻塞，不声称已经完成。

## 交付

按需更新状态、变更证据、设计文档和其他受影响文档，说明完成内容、实际验证、审查发现及处理结果、剩余限制。明确区分自查与独立审查；未独立执行时说明原因。

满足 [提交约定](../../rules/development.md#提交约定) 的条件后，只暂存本次改动并按其中的 CL 描述规范提交；不满足时不提交并说明原因。推送或发布遵循用户授权。交付总结中给出提交哈希和首行。
